### Findings

**1. [criteria] `npm test` FAILS on CI on both platforms — `tests/unit/red-proofs.test.js:414` and `:231`. Band A. Disposition: fix.**
CI runs **Node 20** (`.github/workflows/ci.yml:38-39`); the implementer measured on Node 25.9.0. Two failures, identical on ubuntu-latest and macos-latest, both in the new suite:
- `not ok 1680 — red-proofs: a testNamePattern matching nothing exits 0 with a pass count in Node — and is still an ERROR here (criterion 3)` (`:231`)
- `not ok 1692 — red-proofs: the pinned TAP shapes are observed on the Node running this suite (criterion 4b)` (`:384`, failing at `:414-415`)

Root cause, from the CI diagnostic's own parsed tree: on Node 20 an unmatched `--test-name-pattern` emits **`ok N - <name> # SKIP` per test** (`directive: 'SKIP'`, `ok: true`), not the zero-test `1..0` shape Node 25 emits. So `assert.deepEqual(rp.parseTap(none.stdout, 'tests/suite-basic.js'), [])` at `:415` gets two SKIP nodes.

This is criterion 4b's own compatibility evidence firing red — the criterion that exists exactly to catch this, using "CI's existing ubuntu/macOS matrix" as the evidence. Criterion 13 is unmet and Definition of done items 1 and 5 are unmet. The PR body's `V2 — npm test exit=0` and `V15 — npm test exit=0` are true only on the author's Node 25.9.0; I reproduced them locally and they do not generalise. Node 20 is inside the repo's declared support (`engines: >=18`) and **above** the lane's 18.15.0 floor, so `nodeFloorOk('20.11.1')` returns OK (I checked) and the runner accepts a Node whose TAP it has not validated.

Fix is the implementer's and stays inside the Deliverables: make `parseTap`/`evaluateBaseline` and the two tests accept **both** shapes for an unmatched pattern, and make the criterion-4b test assert version-tolerant invariants rather than a deep-equal against one Node's exact tree. The owner rulings in force forbid the `engines` raise and the Node-matrix expansion, so version tolerance is the only open route. (The *runner* still fails closed on Node 20 — `evaluateBaseline` would throw ERROR on the SKIP directive — so this is a pinning/testing defect, not a silent-pass defect. That is the one piece of good news here.)

**Also route to wd-architect:** Table A's pinned shapes ("Measured on Node v25.9.0") and criterion 3's literal "*measured this round, that prints an inner `1..0` under an outer file-level `ok` and exits 0*" are stated as canonical contract but are Node-25-specific. Measurement has now falsified them on Node 20. The canonical table needs the second data point; do not let the implementer guess which shape is normative.

**2. [contract] The `..` channel between sibling phase copies is open — `scripts/red-proofs.js:883-890`. Band B. Disposition: fix.**
`runProof` creates **all three** phase copies up front, manifest-verifies each at creation, then chmods only their **common parent** to `0500`. Mode `0500` is `r-x`: it blocks creating a new entry *in the parent*, which is the case criterion 7(b2) tests (`../sentinel`) — but it does **not** stop a phase child from traversing into an already-created sibling copy and writing inside it, because those copies carry the source root's mode.

Demonstrated end-to-end against the real runner, on a `mktemp` copy of `tests/fixtures/red-proofs/base` whose suite writes `../red/subject/subject.js` during BASELINE:

```
ERROR        fixture-greeting  (WP-red-proofs-fixture criterion 1)
             tests/red-proofs/base.proofs.json [fixture-greeting] APPLY: "find" occurs 0 time(s)
             in subject/subject.js, "occurrences" declares 1
```

BASELINE's child controlled the bytes APPLY read; a second write planted a file into the `control` copy. This contradicts four contract surfaces:
- Table B row 2b — "NO TWO PHASES SHARE ANY WRITABLE PATH THE RUNNER PROVIDES"; the runner provides all three copies and they are mutually writable.
- Table B row 2 — "verified against the manifest **before use**": the control copy is verified three suite runs before it is used.
- Table B row 4 — "because nothing has executed there the check cannot be raced": a child *has* executed somewhere that can write there.
- Security checklist — "no interval in which suite code can swap the target or a parent for a symlink".

Cheap, local fix that needs no spec change: create and manifest-verify **each phase copy immediately before its own phase** (unlock parent → copy → verify → prepare → relock), so no unused copy exists while another phase's child runs. This is also the more faithful reading of rows 4 and 6's word "FRESH". I am not reopening the LINEAGE frame — the frame closed on *"no shared writable path the runner provides"*, and sibling copies are provided by the runner.

**Also route to wd-architect:** criterion 7(b2)'s four-fixture inventory is a contract surface now known incomplete; the sibling-copy write belongs in it.
