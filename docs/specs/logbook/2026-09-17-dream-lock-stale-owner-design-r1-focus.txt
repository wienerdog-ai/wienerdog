DESIGN REVIEW of a new work-package spec; no product code has been written yet. Review ONLY these two files: docs/specs/WP-dream-lock-stale-owner-loud.md and docs/specs/logbook/2026-09-17-dream-lock-silent-stall.md. Exclude docs/marketing/, memory/research/ and userreports/ entirely. Background: src/core/dream/lock.js acquireLock now keeps an EXPIRED single-run lock when its recorded local PID still exists (signal-0 success or EPERM returns busy); src/cli/dream.js prints one line and returns exit 0 on busy, so the supervisor records success. If a dream died uncleanly and its PID is later held by an unrelated long-lived process, memory consolidation stops forever with no alert. The spec proposes (a) a "proven dead by reboot" takeover: when the recorded startedAt is earlier than the machine boot time estimated as now - os.uptime()*1000, minus a 60 s margin, the owner is proven dead and the existing overwrite path applies; (b) a loud gate: a busy decline more than 6 hours past the lock deadline throws (exit 1, the existing alert path) with a byte-exact plain-language message. Challenge specifically: (1) WRONG TAKEOVER is the worst outcome - two dreams sharing scratch. Find every way the boot estimate can be later than the true boot or startedAt earlier than the true start: wall-clock steps, NTP, timezone/DST (timestamps are ISO/epoch - verify), sleep/hibernate semantics of os.uptime() on macOS, Linux and Windows, containers/VMs where uptime is the host's, suspended-and-resumed processes, a lock file copied or restored from backup. Is a 60 s margin defensible, and is the residual honestly stated? (2) The loud gate: can a LEGITIMATE long-running dream trip it; can it fail to fire when it should (for example because every run takes the busy-within-deadline branch, or the deadline is crafted/huge); does throwing hourly from the catch-up job create an alert storm, and is that priced? (3) Does the byte-exact message leak lock-file bytes or paths it should not, and is it actionable for a non-developer? (4) The proposed ADR-0012 amendment text: does it contradict Table L of WP-dream-live-owner-lock (docs/specs/done/) or the 2026-09-15 amendment it amends? (5) Can every acceptance criterion and RED-proof declaration discriminate a correct implementation from a plausible wrong one, and is the clock/uptime injection seam testable without a real reboot? (6) Does every file:line citation resolve on this tree - verify by reading the files. The "Dispatch precondition - owner items" section lists decisions reserved for the owner as recommendations with overrule costs; disagreeing with a recommendation is a welcome finding, but their being unratified is by design and not itself a finding. Report what you executed versus what you only read.
