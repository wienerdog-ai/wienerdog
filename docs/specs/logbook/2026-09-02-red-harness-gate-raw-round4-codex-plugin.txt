# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

No-ship. The round-3 copy, temp, symlink, CONTROL, TAP, and lineage edits landed, but four material contract defects remain. EXECUTED: Node-version probe 0 (v25.9.0); runner guarded grep absent/compliant/violating 1/0/1; package guard actual/absent 0/1; per-CWD TMP probe 0 (distinct TMPDIRs but common HOME); manifest counterexample 0; scoped/no-match TAP 0/0; full write-dependent dream suite 1 under the read-only sandbox; mirror-walk 0; git status 0/clean; git diff --check 2 on pre-existing trailing whitespace in committed raw records.

Findings:
- [high] The phases still share writable state outside their copies (docs/specs/WP-criterion-red-harness.md:252-254)
  Materiality A — Redirecting TMPDIR/TMP/TEMP and removing dependency links does not establish the universal invariant. Suite code can walk from its copy's cwd to the writable outer wrapper root and place state beside the phase copies; HOME and other ambient writable locations also remain shared because tests/run.js preserves the environment. A BASELINE that creates ../sentinel, a RED that observes/removes it and emits the expected assertion failure, and a CONTROL that then passes satisfies the required phase results with an irrelevant mutation. Criterion 7(b2) tests only the redirected temp path and source symlinks, so it would not catch this. The adopted dream-pipeline suite itself appears safe: setup places home/core/vault below os.tmpdir(), and runDream redirects HOME/WIENERDOG_HOME accordingly; its /tmp literals are classifier inputs or symlink targets, not writes. That does not make the runner-wide claim true for future suites.
  Recommendation: Either use a real filesystem sandbox for suite children, or narrow PROVEN and the isolation invariant to the exact channels actually controlled and declare suites with other writes unsupported. Add a fixture that exchanges a sentinel through the copies' common parent and another through inherited HOME; the current design must not certify either.
- [high] FILTERED can be both a successful exit and a non-successful verdict (docs/specs/WP-criterion-red-harness.md:259-263)
  Materiality B — With two proofs for one criterion, --proof can select one, make that proof PROVEN, and roll the criterion up as FILTERED. V4's literal exit condition then permits exit 0 because every proof that ran reached PROVEN, while its stated purpose rejects partial runs and ADR-0042 says anything other than full criterion proof exits non-zero. The taxonomy is also not exhaustive: ERROR is repeatedly required but absent from V4, and a failed selected proof plus an omitted sibling can simultaneously be FAILED and FILTERED. Implementations can therefore choose incompatible exit codes, including accepting partial evidence in automation.
  Recommendation: Add one authoritative verdict/exit table covering PROVEN, FILTERED, VACUOUS, UNCONTROLLED, UNSUPPORTED, FAILED, and ERROR, including precedence when multiple conditions apply. Explicitly require FILTERED to exit non-zero if partial evidence must never be treated as success, and test that exit code in criterion 6a.
- [medium] The manifest cannot detect all partial or non-equivalent copies (docs/specs/WP-criterion-red-harness.md:252)
  Materiality B — A manifest containing only relative file path, size, and digest cannot observe missing empty directories, changed file modes, or other type/metadata differences. The executed in-memory probe produced identical specified manifests after deleting an empty directory and changing an executable file from 0755 to 0644. A RED copy suffering either phase-specific defect can behave differently from BASELINE and CONTROL while passing manifest verification, defeating the claim that only the mutation differs. Criterion 5's generic partial-copy case can still pass while leaving these omissions untested.
  Recommendation: Define exact manifest equality over all relevant entry types, including directory entries, executable/mode semantics, and rejection of unexpected paths. Explicitly define .git as excluded and root-git-dependent suites as unsupported, then require mode-loss and empty-directory-loss fixtures alongside the missing-file case.
- [medium] The ADR and lane table retain the retired one-run/shared-copy cost model (docs/adr/0042-machine-run-red-proofs.md:66-139)
  Materiality B — The mandatory lifecycle executes BASELINE, RED, and post-RED CONTROL in three copies per proof. Nevertheless, ADR decision 2 and the WP lane table say the suite runs once per mutation, while the ADR consequence still budgets one per-proof copy on top of a shared pristine copy. That directly contradicts the WP's withdrawal of shared baselines. For the two adopted proofs, the actual minimum is six suite executions—about 87.6 seconds at the recorded 14.6 seconds—plus one snapshot and six phase-copy/manifest operations, not roughly two suite runs. This stale durable text can mislead implementation, sizing, and eventual CI planning.
  Recommendation: State three suite executions and three phase copies per proof in both the ADR and Table D, remove the shared-pristine consequence, and record the adopted lane estimate of approximately 88 seconds plus copy/manifest overhead. Reassess size M or take criterion 9's documented severance before dispatch if that measured budget changes the implementation plan.
