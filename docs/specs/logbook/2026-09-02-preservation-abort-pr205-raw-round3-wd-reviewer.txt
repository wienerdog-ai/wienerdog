### Findings

**1. `[contract]` Band A — `tmpOwned` is set one statement too late, so a mid-write failure abandons partial secret-bearing bytes. Regression introduced by `40225aff`.**
`src/core/dream/validate.js:723-724`

```js
fs.writeFileSync(tmp, content, { mode: 0o600, flag: 'wx' });
tmpOwned = true;
```

`flag: 'wx'` is `O_CREAT|O_EXCL`: the directory entry is created **inside** that call, and any failure *after* the create — `ENOSPC`, `EDQUOT`, `EFBIG`, `EIO`, a failed `close` — throws with `tmpOwned` still `false`. The catch then skips `removeOwnedQuarantinePath(tmp)` and the file this invocation created stays on disk. The block comment at `:718-722` states the rule as intended — *"`EEXIST` (**or any other write failure**) falls straight into the catch below with `tmpOwned` still false"* — and that parenthesis is the bug: only `EEXIST` means "not ours".

**Reproduced with no `fs` patching whatsoever**, under `ulimit -f 1` with `SIGXFSZ` ignored, so the kernel returns `EFBIG` from `write(2)` after `O_EXCL` has already created the file:

```
prev  (c7ff8f12) ret=null  dir=[]                    D1 satisfied = true
head  (40225aff) ret=null  dir=[".tmp-87922-x.md"]   D1 satisfied = false
                           sizes=[512]   ← 512 bytes of the judged content
```

Same probe, same injection, two trees — so this is a regression of the round-3 commit, not a pre-existing condition.

It violates two things verbatim:

- **Table D row D1** — *"the temp write was ATTEMPTED, and the rename has NOT completed — so **a partial or complete secret-bearing temp file may exist**"* → required: *"remove `tmp` and **confirm it is absent**"*. This is exactly that state, and `tmp` is neither removed nor confirmed absent.
- **Acceptance criterion D4** — *"after **any** preservation failure, the `tmp` this call wrote … [is] absent"*. This call wrote it; it survives.

Two consequences make it Band A rather than Band B:

- **The bytes are unreachable and invisible.** `listSecretQuarantine` (`src/core/digest.js:858`) filters `!e.name.startsWith('.')`, so a `.tmp-…` leftover never reaches the banner, the preservation record, or the abort message. That is Table D row D3's own stated harm — *"secret-bearing bytes remain on disk under a name no preservation record, no cleanup pass and no abort message can reach"* — now produced by the code the table governs.
- **It self-poisons.** Once the leftover exists, every later preservation of that note under the same pid hits `EEXIST` and returns `null` forever. I measured two consecutive runs after seeding the residue: `null`, `null`. A transient disk-full becomes a permanent preservation outage for that note — which then feeds P0 and aborts the run every night.

**Why the suite stays green:** every existing D1/D4 fixture injects the failure by throwing from `writeFileSync` *without calling through* (`tests/unit/dream-validate.test.js`, the `.tmp-` guard in the D1 and D4 tests), so no file is ever created and the create-then-fail state is unreachable by the current evidence. A new RED is needed alongside the fix: inject a failure that **calls through to create** and then throws, and assert the `tmp` is absent.

*Disposition: **fix.*** I verified a minimal, seam-preserving fix end to end — full suite **exit 0, 2455 pass / 0 fail**, the genuine `EFBIG` case now `dir=[]`, and the foreign-leftover protection intact (`ret=null`, foreign byte-identical):

```js
try {
  fs.writeFileSync(tmp, content, { mode: 0o600, flag: 'wx' });
} catch (err) {
  // EEXIST is the ONLY outcome in which the path is not ours: a foreign
  // crash-leftover under a reused pid. Every other failure happened AFTER
  // the exclusive create, so the file exists and IS ours (Table D row D1).
  if (!err || err.code !== 'EEXIST') tmpOwned = true;
  throw err;
}
tmpOwned = true;
```

**A warning on the obvious alternative:** I first tried splitting the call into `openSync(tmp,'wx',0o600)` → `tmpOwned = true` → `writeFileSync(fd, content)`. It fixes the gap, but it **breaks 8 existing tests** (`FI-13 tracked/untracked`, `R1`, `R0b tracked/untracked`, the `P0b regression`, D1 and D4), because those fixtures patch `writeFileSync` and match on `typeof p === 'string'` — an fd is a number, so the injection silently stops firing. Do not take that route without rewriting those fixtures.

Also update the two ownership prose surfaces once fixed: the block comment at `:646-655` (*"`tmp` becomes this invocation's OWN path only once the exclusive create succeeds"* — correct as written, but the code records it later than that) and `quarantinePreserve`'s `@throws` at `:686-688`, which promises D3 disposal of *"the path this invocation owns (`tmp` before the rename …)"*.
