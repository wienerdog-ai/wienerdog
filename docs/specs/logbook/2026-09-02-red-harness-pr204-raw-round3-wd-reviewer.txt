### One new finding

**[contract] The declaration digest tie does not cover **addition** — `scripts/red-proofs.js:372-386`. Band C. Disposition: fix (3 lines) or record as residual. Non-blocking.**

`assertDeclarationsMatchSnapshot` iterates the **LOAD-time** digest map, so it sees a file that changed or vanished but not one that appeared. Demonstrated with the `afterLoad` hook, adding a third proof for the *same* `(wp, criterion)` the fixture already declares, unfiltered:

```
verdict: PROVEN  exit: 0
2 declared proof(s), 2 selected
snapshot: 22 entries          ← the added declaration IS in the snapshot
PROVEN  WP-red-proofs-fixture criterion 1 — fixture-greeting=PROVEN; fixture-arity=PROVEN
RUN: PROVEN
declaration files on disk at end: base.proofs.json, zz-extra.proofs.json
```

A criterion reports **PROVEN, exit 0** on 2 of the 3 declarations the snapshotted tree holds — the partial-evidence shape Table B row 7 and `FILTERED` exist to prevent, and row 2's rules-out column names "a concurrent edit to `--root` mid-run".

Why it is Band C and not blocking: the uncaught window is narrow and specific — LOAD → `buildManifest(root)`. An addition landing between `buildManifest` and `copyTree` is already caught by `verifyCopy`'s `extra:` check. Declarations are committed repo content, not adversary input (the spec's own security checklist says so), so this needs the developer to write into their own checkout during a sub-millisecond window. And it cannot manufacture a false proof: every proof that ran was genuinely proven; only the roll-up is incomplete. The fix is small — require the snapshot's `*.proofs.json` name set to equal LOAD's — and I'd take it because the guard is new and the fix is shorter than the disclosure would be, but I would not hold the PR for it.
