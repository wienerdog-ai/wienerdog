# Codex Adversarial Review

Target: branch diff against main
Verdict: needs-attention

No-ship. R2-B and R2-C are genuinely closed; R2-A’s original same-copy symlink race is removed, but phase isolation is still bypassable through shared temp/dependency state. CONTROL can also report false PROVEN without proving copy equivalence. SCOPE OBJECTIONS: none—the unsigned doctrine, CI lane, and repository engines floor do not drive this verdict. EXECUTED: Node v25.9.0 probe exit 0; assertion/thrown/nested TAP probes each exit 1 and emitted ERR_ASSERTION/ERR_TEST_FAILURE/subtestsFailed as specified; copy-with-symlink probe exit 1 because the read-only environment denied mkdtemp with EPERM, so no copy result; guarded runner/package greps exited 1/0; mirror-walk and lint exited 0; git diff --check exited 2 on trailing whitespace in the round-2 shadow raw.

Findings:
- [high] Fresh repository copies still share writable state across phases (docs/specs/WP-criterion-red-harness.md:252-253)
  Materiality A — Table B treats a fresh repository directory as phase isolation, but every suite inherits the same wrapper-owned TMPDIR/TMP/TEMP for the entire runner invocation, and the suggested copies link to the same real node_modules. BASELINE suite code can leave state in the shared temp root or write through the dependency link; RED then observes those changed bytes from its nominally fresh copy. The dependency write also escapes the wrapper root. The claim that links are “resolution-only by construction” constrains runner writes, not arbitrary suite writes. The original target-swap race is closed, but the mutation can still be irrelevant while the expected assertion reddens because BASELINE affected RED.
  Recommendation: Give every suite phase a unique temp subroot and independent dependency state. Do not expose a writable real node_modules target; copy required dependencies per phase or enforce a genuinely read-only mechanism. Add fixtures where BASELINE writes a temp sentinel and attempts a dependency-link write, requiring no cross-phase observation and no external modification.
- [high] CONTROL does not establish that mutation is the only difference (docs/specs/WP-criterion-red-harness.md:257)
  Materiality A — CONTROL may reuse a green obtained before RED and explicitly accepts the resulting drift blind spot. Moreover, independently copying a mutable --root does not make the copies equal “by construction”: there is no frozen source snapshot, manifest comparison, or copy-completion condition, and BASELINE green proves only that selected tests passed—not byte equivalence. A concurrent edit, silently omitted file, shared-state change, or suitable flaky transition can therefore produce the named red while an irrelevant declared mutation still reports PROVEN. Reporting which green was used only exposes the weakness; it does not prevent false certification.
  Recommendation: Create one verified immutable master snapshot before running suite code and derive every phase copy from it. Treat every copy error or manifest mismatch as ERROR. Require a fresh post-RED pristine control for PROVEN; baseline-only evidence should receive a weaker verdict. Add ambient-drift, partial/different-copy, and pass-then-red-with-irrelevant-mutation cases.
- [medium] The supported TAP contract is verified only on Node 25.9 (docs/specs/WP-criterion-red-harness.md:220-229)
  Materiality B — the lane claims support from Node 18.15 upward, but the assertion/error/ancestor shapes are measured only on v25.9. Node explicitly documents that exact reporter output is subject to change between versions ([Node v20 test documentation](https://nodejs.org/download/release/v20.0.0/docs/api/test.html)). Loud failure on an absent field prevents a false positive, but it can make the lane falsely unusable on a supported Node release. No acceptance criterion requires the parser to run on Node 18.15 or 20, so an implementation can satisfy this spec on v25 while breaking the advertised lane range. R2-B fixed flag availability, not reporter compatibility.
  Recommendation: Pin and execute assertion, thrown-error, nested-propagation, skip and no-match fixtures on the oldest lane version and every supported Node major. Alternatively, define an explicitly narrower lane compatibility set or consume a stable runner-owned event serialization instead of version-sensitive TAP text. This does not require raising package.json engines.
- [medium] ADR-0042 still mandates the retired restore model (docs/adr/0042-machine-run-red-proofs.md:47-105)
  Materiality B — Decision 1 says the runner “restores, and requires green again,” and Decision 4 bases attribution on “a restore that returns the suite to green,” while Decision 3 says nothing is restored and the WP permits CONTROL to reuse a pre-RED baseline. If signed as written, the durable doctrine would contain incompatible phase and causality requirements, allowing reviewers or successor specs to demand different implementations and potentially reintroduce mutation-after-suite writes.
  Recommendation: Before signature, replace both restore references with the exact fresh-copy CONTROL rule, including whether a post-RED pristine run is mandatory. Make Decisions 1, 3 and 4 describe one phase order and one causal evidence requirement.
