Review ONLY: docs/specs/WP-dev-descriptor-no-tree-hash.md and docs/specs/logbook/2026-09-17-dev-descriptor-no-tree-hash-round-zero.md. Exclude docs/marketing/, memory/research/ and userreports/ entirely. Background: Wienerdog's scheduler writes a per-job authorization descriptor; an independent launcher verifies it before a scheduled job runs. For a DEV-stance install (the app runs from a source checkout), src/scheduler/descriptor.js buildDescriptor computes a digest of the whole app tree, but reduceForDigest rebuilds the dev appRelease as {stance, root} only, so that tree digest is never part of what is authorized - while the tree walk itself can throw ENOENT when git or npm unlinks a file mid-walk, which makes the scheduled job refuse. The spec proposes to stop computing the tree digest for dev stance, and says ADR-0028's owner-signed 2026-07-25 amendment section 1 already states exactly this contract. Challenge specifically: (1) SECURITY: does removing the dev-stance tree hash weaken anything the launcher or any other consumer actually checks today - find every reader of appRelease.treeDigest and of the descriptor's appRelease in src/ (launcher, run-job, doctor, sync, vendor) and confirm none relies on it for dev stance; can an attacker who can write the app tree gain anything they could not already do in dev stance; is the prod-stance path provably unchanged byte-for-byte; (2) is the claim about ADR-0028's amendment TRUE - read docs/adr/0028 in full at the cited lines and confirm it is Accepted and signed and says what the spec says; (3) migration: what happens to descriptors already written with a treeDigest field for dev stance - does the launcher accept them, does the next write churn or not, is `changed` reported truthfully; (4) the spec says its end-to-end dev-fire scenarios are not run by npm test and print SKIPPED with exit 0 when an env var is unset - can a PR therefore pass every required check without ever exercising the dev path, and does the spec make the implementer run them and paste the output; (5) can every acceptance criterion and each of the three RED-proof declarations discriminate a correct implementation from a plausible wrong one; (6) do all file:line citations resolve on this tree - verify by reading the files; check both ends of cited ranges. The "Dispatch precondition - owner items" section lists decisions reserved for the owner as recommendations with overrule costs; disagreeing with one is a welcome finding, their being unratified is not. Report only product-behaviour findings in the main list; list verification-machinery findings separately, marked as machinery. Report what you executed versus what you only read.
