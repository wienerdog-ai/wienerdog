- [high] Rejected-artifact cleanup omits the pre-rename temporary file and durable deletion (docs/specs/WP-preservation-abort-widening.md:342)
  Materiality B. The first file fsync occurs before rename, so an fsync failure leaves the secret-bearing bytes in `tmp` and no owned artifact at `dest`. P0b nevertheless requires every durability failure to remove the FINAL DESTINATION and asserts that `dest` exists. The existing catch treats `tmp` removal as best-effort, and the acceptance criteria only demand destination/tree evidence for post-rename mismatch and read-error cases. An implementation can therefore report preservation failure while an undeletable, unrecorded `.tmp-*` file remains. Conversely, blindly deleting `dest` before a successful rename can target a candidate path this invocation never owned. Post-rename disposal is also not crash-durable: the spec requires unlink plus confirmation but no directory fsync after unlink, so the rejected directory entry can reappear after a crash—the same failure model P0b added fsync to address.
  Recommendation: Specify an ownership-state cleanup protocol: before successful rename, remove and confirm `tmp`; after successful rename, remove and confirm only `dest`; never delete `dest` unless this invocation completed the rename. Failure to clean either owned path must fail loud. After removing a renamed artifact, fsync the quarantine directory before reporting disposal complete.
