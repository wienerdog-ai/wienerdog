Findings:
- [high] [Band A] F8 still allows a foreign destination to be deleted before the descriptor is pinned (docs/specs/WP-quarantine-preserve-durability.md:923-940)
  The descriptor is acquired only after `renameSync(tmp, dest)`, and `stillNamed` runs only after the byte comparison and flush. Two overlapping runs can select the same absent `dest`; run B can rename over run A and finish successfully before A opens the pathname. A then reads B's different bytes, short-circuits before `stillNamed`, leaves `replaced` false, and executes the prescribed `if (!replaced) removeOwnedQuarantinePath(dest)`. This deletes B's successful—potentially only—copy. QPD-5 injects replacement from inside the artifact flush, after A already has its descriptor, so both F8 RED proofs miss this earlier window. Round 1 therefore closed the read-versus-flush inode split but not the ownership split between rename and open.
  Recommendation: Bind ownership to an inode before exposing `dest`, preferably by opening `tmp` with `wx`, writing and verifying through that same descriptor, retaining it across the rename, and migrating the seven write injections. At minimum, require cleanup to verify `dest` against a pre-rename identity before removal. Add a test and RED proof that replaces `dest` between rename and open with different bytes and asserts failure without removing the replacement.
- [high] [Band A] Path-resolved sequence tests can flush the wrong directory inodes (docs/specs/WP-quarantine-preserve-durability.md:529-555)
  QPD-3/QPD-4 map each descriptor to the pathname passed to `openSync`, but never establish that the descriptor's directory inode is the one occupying that path at the final success gate. A same-UID process can rename the real `qdir` aside, place another directory at `qdir`, let the implementation open/fsync that replacement, restore the original before `stateDir` is flushed and before F8's final `dest` stat, and obtain the exact expected path sequence plus a passing artifact `(dev, ino)` check. The original directory containing `dest` was never flushed, so success is reportable without F2 completing for the directory entry actually naming the artifact.
  Recommendation: Retain descriptors for every directory in the chain through the last gate and compare each descriptor's `(dev, ino)` with the pathname then occupying that chain position, using bigint stats. Add a race test that swaps `qdir` during its flush and restores it before the final artifact check; it must fail rather than report success.
- [high] [Band A] QPD-2 does not test the claimed ANY-target failure contract (docs/specs/WP-quarantine-preserve-durability.md:527-533)
  The five injections cover artifact `fsyncSync`, plus `openSync` and `fsyncSync` for `qdir` and the anchor. They omit the artifact `openSync`, both failure points for the always-present `stateDir`, and both failure points for the redacted arm's intermediate shelf. An implementation can ignore or mishandle failures only at one of those omitted sites while passing QPD-2, both sequence identities, and both failure-swallowing RED proofs. This is directly a criterion that a wrong implementation passes.
  Recommendation: Expand QPD-2 into the complete distinct-site matrix: artifact open/fsync; withheld qdir open/fsync; redacted qdir and intermediate shelf open/fsync; stateDir open/fsync; anchor open/fsync. Assert `null`, ownership-correct cleanup, and the applicable shipped P1/P2 or P3 abort for every case; add path-specific mutations for currently omitted middle-chain failures.
- [high] [Band A] V1 accepts a contradictory durability over-claim (docs/specs/WP-quarantine-preserve-durability.md:1153-1214)
  Criterion 7 says both that the approved sentence appears exactly once and that no other sentence claims the copy is on the medium. V1 only counts the approved sentence after flattening JSDoc and checks that some `fs.fsyncSync(` text exists. A source file containing the approved sentence once plus a second statement such as “the preserved copy is safely on disk” passes V1, Table C, and the test suite while making exactly the platform-level over-claim this WP classifies as forbidden.
  Recommendation: Make the durability JSDoc block itself byte-exact, not merely one sentence within unrestricted prose, and have V1 reconstruct and compare that complete block. Require review of any other changed durability-related prose in `validate.js`; a positive exact-sentence count cannot prove the absence of contradictory claims.
