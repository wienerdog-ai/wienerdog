N1 [contract] SHOULD-FIX (blocker-adjacent, and it weakens the F1 mitigation) -
   the pair-atomicity refusal names two preserved copies, unattributed, and the
   wrong one comes first.
   promote.js:914-919. Phase 1c builds the sibling's refusal by embedding the
   sibling's ALREADY-DECORATED reason string, then applies withPreserved again
   with the sibling's own artifact. Reproduced out-of-band (script run under
   os.tmpdir(), removed; nothing written into the repo) with both halves of a
   skill/ledger pair redacted and the ledger refused by its gate:

     { rel: "05-Skills/x/LEARNINGS.md",
       reason: "ledger fails policy (an unredacted copy was preserved as `ledger-copy.md`)" }
     { rel: "05-Skills/x/SKILL.md",
       reason: "paired with `05-Skills/x/LEARNINGS.md`, which was refused: ledger fails policy
                (an unredacted copy was preserved as `ledger-copy.md`)
                (an unredacted copy was preserved as `skill-copy.md`)" }

   Because escalated blocker 1 leaves no typed carrier, the report package must
   read the artifact name OUT OF THIS STRING - and the first match in SKILL.md's
   reason is the OTHER FILE'S copy. Per Table Q row Q3 that string is the user's
   only route back to their copy, so pointing them at the sibling's artifact is
   the same class of harm the mitigation exists to prevent, just narrower. The
   deliverable test's case (b) does not catch it because only the SKILL side is
   redacted there.
   REMEDY (implementer's, inside the existing shape): attribute the clause -
   withPreserved(reason, preserved, rel) producing "an unredacted copy of
   `<rel>` was preserved as `<artifact>`" - or build the pair refusal from the
   sibling's UNDECORATED reason (keep a rawRefuse on the decision) so only one
   clause is ever appended. Add a pair case where BOTH halves are redacted.
