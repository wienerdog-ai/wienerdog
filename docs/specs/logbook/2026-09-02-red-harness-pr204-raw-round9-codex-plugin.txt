The runner leaves a standard checkout path available as shared phase state and cannot faithfully identify some valid test names. Both can invalidate the core guarantee that a PROVEN result corresponds to isolated, exact named assertions.

- [P1] Redirect inherited PWD into the phase copy — /Users/gyulafeher/Documents/Claude_Projects/wienerdog-wt/criterion-red-harness/scripts/red-proofs.js:686-686
  When invoked from a normal POSIX shell or npm, spreading `process.env` preserves `PWD` as the real checkout, because spawning with `cwd: copyDir` does not update that environment variable. A suite using `process.env.PWD` can therefore read or write shared checkout state across BASELINE, RED, and CONTROL, potentially producing a false PROVEN or modifying the source tree, contrary to [Table B row 2b](docs/specs/WP-criterion-red-harness.md#L289). Set `PWD` to `copyDir` before spawning the phase.

- [P2] Preserve control characters in TAP identities — /Users/gyulafeher/Documents/Claude_Projects/wienerdog-wt/criterion-red-harness/scripts/red-proofs.js:834-835
  For legal names containing controls, such as an actual newline in `test('a\nb', ...)`, Node's TAP reporter emits an escaped spelling that this function leaves as the literal characters `a\nb`; that spelling can also represent a test whose name literally contains backslash-plus-`n`. Consequently an exact declaration can fail to match its test or bind to the wrong test, even though [Table A](docs/specs/WP-criterion-red-harness.md#L193) permits any non-empty exact hierarchical name. Decode identities without this collision or reject ambiguous names during validation.
