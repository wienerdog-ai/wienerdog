Findings:
- [high] [A] F10 omits two destructive temp-name check-to-unlink windows (docs/specs/WP-quarantine-preserve-durability.md:580)
  F10 claims exactly three residuals and says only residual (c) destroys anything. The prescribed sequence contains the same irreducible TOCTOU at both temp removals. After a successful link, `ownsName(tmp, fd)` can return true, the user can replace `tmp`, and `removeOwnedQuarantinePath(tmp)` deletes the replacement; the held fd and `dest` remain valid, so the invocation can subsequently report success. When the commit throws, the catch computes `ownedTmp`, closes the fd, and only then removes by pathname; a replacement inserted after the gate is likewise deleted on the failure path. Neither window is among (a)–(c), and item 6 prices only the destination failure removal.
  Recommendation: Add both exact temp check-to-unlink windows to F10 and price their cleanup alternatives in the owner decision, or redesign the removals so the contract can truthfully exclude them. Update all F10 mirrors accordingly.
- [high] [A] The retained create-failure heuristic can delete a path the new primitive never created (docs/specs/WP-quarantine-preserve-durability.md:1245-1274)
  The spec requires replacing `writeFileSync` with a single `openSync` while leaving the inner catch's `tmpOwned` disjunction byte-unchanged. That heuristic existed because `writeFileSync` combines create and write and can throw after creating the file. With `openSync`, a successful create returns the fd; when it throws, no descriptor proves ownership. Nevertheless, every non-EEXIST error sets `tmpOwned`, and the outer catch removes `tmp` without an identity gate. After an ENOSPC/EACCES-style create failure, a user substitution before cleanup is therefore deleted. This is an additional undisclosed destructive failure window; `d1-cleanup-not-gated` covers only the `fd >= 0` commit-failure state.
  Recommendation: Do not carry the old non-EEXIST ownership inference into the standalone `openSync`. Treat `fd < 0` as owning no pathname; after a successful open, use the descriptor gate for write or commit failures. Add a narrow proof for create failure followed by a foreign temp-name insertion.
- [medium] [B] Canonical F1 still instructs the rejected pathname-write design (docs/specs/WP-quarantine-preserve-durability.md:571)
  Table F declares itself canonical, but F1 says the write remains pathname-based because descriptor writing would require position management. F8 and the byte-exact source form instead require `writeAllAt(fd, content)` with explicit positioning—the round-4 provenance fix. An implementer following the canonical row can recreate the create-to-open adoption window. Later proof/source-form checks should catch this, so it is downstream-caught rather than silent.
  Recommendation: Rewrite F1 to require the exclusive-create descriptor and explicit-position write. Remove the obsolete pathname-write rationale from the later trap prose as part of the same mirror sweep.
