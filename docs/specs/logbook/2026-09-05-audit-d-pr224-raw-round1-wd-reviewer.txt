### Findings

**1. [contract] `tests/red-proofs/audit-d-code-derived-recipients.proofs.json:82-90` — `reply-grammar-dropped` declares two identities where Table C's Signal column declares one. This is a SPEC contradiction; route to wd-architect. Band B.**

The shipped `expectRed` names both `[AUD-D3]` and `[AUD-D2]`. Table C's row for this proof (spec `:644`) has Signal `[AUD-D3]` only. The spec's own discipline paragraph (`:663-669`) is explicit and pre-warns about exactly this case:

> `expectRed` sets are MEASURED after implementation, never predicted — and a mutation whose measured set EXCEEDS its declaration is **restated, not widened into the declaration**. The worked case: a "take the first `<…>` candidate" mutation of step 3 also reddens `[AUD-D2]`'s quoted-display-name row … the fix is a narrower mutation, because widening the declaration would make the pair stop distinguishing the two identities.

The implementer applied that rule correctly to `reply-candidate-count-ungated` (narrowed to "first address-shaped substring", measured `[AUD-D3]`-only) and then widened here — but they were following Table C's own parenthetical, which prescribes the broad mutation verbatim: *"(take the whole trimmed value as the address)"*. `replace: "  const address = trimmedSelected;"` is the literal execution of that parenthetical, and it **necessarily** reddens `[AUD-D2]`, because every angle-addr accepted row then yields the whole `phrase <addr>` string as `to`.

So Table C's row-level parenthetical and the expectRed-discipline paragraph cannot both be satisfied. The PR body's "Decisions made" #4 ("No `expectRed` set needed widening") is inconsistent with what shipped, but the implementer had no non-guessing choice.

- **For wd-architect**: reconcile spec `:644`'s parenthetical with `:663-669`. The narrow mutation that satisfies both the paragraph and the semantic description ("accept the selected value without matching Table B's single-mailbox grammar") is `replace` → `const address = match ? match[1] : trimmedSelected;` with the `if (!match) throw` line removed — every `[AUD-D2]` accepted row still matches the grammar and is unmoved, while all twelve `[AUD-D3]` step-3 fixtures draft instead of refusing.
- **For the implementer, only after that ruling**: if the architect narrows the parenthetical, re-`find`/`replace` and **re-measure** the set (`node scripts/red-proofs.js --wp WP-audit-d-code-derived-recipients`) — never predict it.

**2. [criteria] `tests/unit/broker-verbs.test.js:310` — the only assertion under an `[AUD-D*]` identity that carries neither its band marker nor an error validator. Band C (latent proof-lane trap).**

```js
await assert.rejects(() => r2.callTool('create_draft_to_self', { subject: 's', body: 'b', ...extra }));
```

Two problems, both one-line fixes:
- Spec `:630-632` makes the marker a universal: *"Each identity carries its band marker in **every** assertion message, so each declaration's `signal` is a string the author writes rather than a guess."* `evaluateRed` enforces this by `hit.node.diag.raw.includes(entry.signal)` (`scripts/red-proofs.js:1658`), and the TAP diagnostic carries the assertion message, not the test name — so any future mutation that lands on this line fails the signal check rather than reporting a clean red. I scanned all three suites: **59 of 60** assertions under `[AUD-D*]` identities carry their marker; this is the one.
- Criterion 2 requires the argument object be *"**schema**-rejected with zero Google calls"*. With no message and no error validator this asserts only "it rejects for some reason". The zero-calls half on `:311` is correctly marked and does carry the safety substance, so this is not a hole in the property — only in what the assertion pins.

Fix: add the validator and the marker, e.g. `(err) => /additionalProperties|not allowed|unknown/i.test(err.message)` plus `` `[AUD-D1] a supplied ${Object.keys(extra)[0]} is schema-rejected` ``.

**3. [quality] `tests/unit/broker-verbs.test.js` `[AUD-D4]` To-block (last block of the identity) — the second clause of criterion 5's UTF-16 branch is argued in a comment but not asserted. Band C.**

Decision 1 (step 4 read as `.length`) is legitimate — the spec deliberately leaves the unit open (`:810-818`). Under that branch criterion 5 requires the assertion *"step 4 refuses, **and no `To` line over 998 octets is reachable at all**"*. The test asserts the first clause only. I verified the second clause independently and it **holds**: with 320 UTF-16 code units and a maximum of 3 UTF-8 octets per code unit (astral pairs are 2 octets/unit), the largest grammar-admissible `To` line is `4 + 320×3 = 964` octets, and an empirical 320-code-unit all-3-octet address produced a conforming line. Optional: pin it with that one witness so the claim does not live only in a comment.

**4. [quality] `src/gws/broker/verbs.js:170-176` — `create_draft_to_self`'s model-supplied `subject` has a 512-**character** schema cap but no octet bound, so a 512-char `€` subject emits a 1545-octet `Subject:` line. Band C, not a regression, correctly out of scope.**

`send_digest_to_self` has the identical shape today, and the spec confines step 7 to `create_reply_draft` (`:434`, `:483-486`) and files the sibling `From` gap under "Discovered issues" (`:481`). Flagging only so it is a deliberate carry-forward: the ruled step-7 output bound now covers four lines built by one verb, while two other verbs still emit an unbounded model-supplied `Subject`. Worth a follow-up WP alongside owner item 10's named successor candidate (c).
