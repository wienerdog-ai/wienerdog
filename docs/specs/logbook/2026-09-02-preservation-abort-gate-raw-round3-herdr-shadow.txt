Body: P0b’s ordering is correct for an existing directory—file fsync, rename, directory fsync—but `quarantinePreserve` recursively creates `quarantine/` or `quarantine/redacted/`. Syncing only the new `qdir` does not durably persist that directory’s entry in its parent. On first use, a crash after workspace teardown can therefore lose the entire newly created directory and the only artifact. Linux explicitly requires syncing the containing directory for a directory entry; this applies recursively to newly created directories ([Linux fsync(2)](https://www.man7.org/linux/man-pages/man2/fsync.2.html)). On macOS, Node/libuv normally tries `F_FULLFSYNC`, but silently falls back through `F_BARRIERFSYNC` to `fsync`, while Node documents the guarantee as OS/device-specific ([libuv fs.c](https://github.com/libuv/libuv/blob/v1.x/src/unix/fs.c), [Node fsyncSync](https://nodejs.org/api/fs.html#fsfsyncsyncfd)). The unconditional “survive a crash/on the medium” claim is therefore broader than the prescribed steps.  
Recommendation: Require durable creation of every newly created directory by syncing each affected parent bottom-up, or prove those directories preexist durably. Define supported filesystem semantics and treat an unavailable required flush as preservation failure that retains the workspace.

Body: P0b says every durability or verification failure removes the final destination and asserts that `dest` exists. That is false when file fsync or rename fails before rename: only secret-bearing `tmp` exists, and the current catch still treats its cleanup as best-effort and suppresses removal failure. Thus EIO/ENOSPC before rename can return `null` while leaving an unrecorded temporary artifact, especially unannounced under `redacted/`. Post-rename cleanup is also only observably absent unless the directory is fsynced after unlink; a crash can resurrect the rejected entry. The mismatch/read-error criteria never exercise either pre-rename cleanup or durable deletion.  
Recommendation: Specify an ownership state machine: before successful rename, confirm `tmp` removal; afterward, confirm `dest` removal; any cleanup failure escapes as `WienerdogError`. After unlink, fsync the containing directory. A plain `null` is valid only once the owned path is absent and that deletion is durable.
