Review ONLY docs/specs/WP-dream-collect-parse-throw-quarantine.md and docs/specs/logbook/2026-09-17-dream-collect-parse-throw-quarantine.md. Exclude docs/marketing/, memory/research/ and userreports/ entirely. Please review by READING the code and reasoning about control flow; do not construct or execute malformed input files - the spec's own logbook already records the reproduction, and this round is about the design of the fix. CONTEXT: the nightly dream job collects session transcript files with src/core/dream/scratch.js collectExtracts, which calls the transcript parsers (src/core/transcripts/claude.js, codex.js, index.js) inside its admission loop. The parsers join content-block text values with Array#join at four sites without first checking that each value is a string, so a transcript file in which a text value is an unexpected type (an object, a number) makes the parser throw a TypeError instead of returning a result. Because the collector has no try/catch around the parse, one such file aborts the entire nightly run, and since the file is never recorded in the quarantine ledger, the same file aborts the next night's run too, until the user notices and removes it. The spec also measured two more content-driven exceptions outside the parser: sanitize(extract.session_id) when the session id is not a string, and the scratch-file write failing with ENAMETOOLONG when the id is very long. THE DESIGN (size S): a per-file error boundary in collectExtracts from the parse call through the JSON serialisation of the extract; an exception inside it is recorded through the existing recordQuarantined as a new reason `parse-threw` (same five ledger fields; the catch binds no variable, so only the code-owned reason literal and the file's existing identity fields become durable - never the exception message); the loop continues with the next file; the scratch-file write stays OUTSIDE the boundary so a genuine disk failure still fails loudly; sanitize gains a 128-character bound so the write cannot fail on the id's length; a file recorded this way is retried when it changes (existing fingerprint rule); dry-run inherits the boundary and persists nothing; the new reason is informational and decays like the others, and no code path reads the reason to decide anything; hardening the parsers themselves is deferred to a successor package as an owner item; the run report section from a sibling package already covers the new reason under its newly-quarantined count with no wording change; src/cli/doctor.js may need the new literal so it does not print "not recognized". Challenge by reading: (1) COMPLETENESS - enumerate every statement in collectExtracts' per-file path that can throw because of the file's CONTENT (not I/O), and say for each whether it is inside the boundary, outside on purpose with a stated reason, or missed; (2) MASKING - the stream reader already converts open/read failures (permission errors, EMFILE) into a non-ok outcome before the parser runs; is there any remaining path by which a genuine infrastructure failure would now be recorded as parse-threw against a healthy file, and does the design distinguish content errors from I/O errors well enough; (3) THE RECORD - can any bytes from the file's content reach the ledger, reports/warnings.md, the digest banner, the run report or doctor output through this path; does the 128-character sanitize bound change the scratch filename of any legitimate existing session with a long id, and thereby its gate evidence or quarantine key; (4) ADR-0023 - is a new quarantine reason permitted without an amendment, and does the retry-on-change and decay behaviour match its amendments; (5) the sibling WP-dream-primary-dialogue-collection (Ready, being implemented now) rewrites the same call site and asserts sanitize is unchanged - does the spec name that interaction and say who rebases; (6) can each acceptance criterion and each RED-proof declaration discriminate a correct implementation from a plausible wrong one (the spec notes the RED runner accepts only assertion failures as red - is every declared red an assertion failure?); (7) do the file:line citations resolve on this tree. Report findings about PRODUCT behaviour in the main list; verification-machinery findings separately, marked as machinery.
